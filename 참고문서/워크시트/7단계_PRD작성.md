# 7단계. PRD(제품요구사항문서) 작성

> 아래는 1~6단계 전체를 종합한 요약. 전체 원본은 `참고문서/우리집식당_통합본_v0.6.md`에 이미 있고, 이 표는 그 내용을 8개 섹션 형식에 맞춰 재정리한 것.

## ① 전체 내용을 섹션별로 종합하기

| PRD 섹션 | 핵심 내용 요약 |
|---|---|
| ① 프로젝트 개요 | 우리집식당 — 가족의 저녁 식사 참여 여부를 매번 다시 묻지 않아도 되게 하는 가족 식사 조율 앱. 1인 1링크 무가입 응답이 핵심 진입장벽 제거 장치. 정적 HTML 목업 35개 화면으로 전체 흐름 검증 완료, 실제 개발은 별도 저장소에서 착수 예정. |
| ② 문제 정의 | 결정과 기록이 흩어져 있고 다음 식사에 재사용되지 않아서, 조율이 매번 처음부터 반복된다(2단계 5 Whys 근본원인). 답변 지연·계획 변경·기록 단절이 구체적 페인포인트. |
| ③ 타겟 사용자 | 3단계 최종 페르소나 "이정숙"(40대 후반, 가족 식사를 주로 준비/조율) + 응답하는 나머지 가족(가입 여부 무관) + 초대받은 비회원 손님(무가입 참여자). |
| ④ 핵심 기능 명세 (Must 기준) | 4단계 MoSCoW Must 16개 전부: 가구·구성원 등록, 식사 생성, 1인1링크·무가입응답, 먹어요/안먹어요, 도착시간, 미응답분리, 준비인원계산, 확정경고·확정허용, 오늘의식탁 확정, 식사카드·달력, 개설자·참여자권한, 응답변경감지·알림, 식사자동기록, 지난구성재사용, 반복손님저장, 월요약통계. |
| ⑤ 화면 구성 및 사용자 흐름 | 4단계 사이트맵(정적 목록) + 5단계 워킹 스켈레톤(동적 흐름) 그대로. 핵심 루프: 홈→식사만들기→링크공유→참여자응답→확정전요약→오늘의식탁완성. |
| ⑥ 데이터 구조 | 6단계 Supabase 테이블 21개(households, household_members, meals, meal_participants 등). 핵심 설계 결정: 비회원 손님은 `users` 계정 없이도 `household_members`/`meal_participants`에 존재 가능해야 함(무가입 응답 원칙과 직결). |
| ⑦ 비기능 요구사항 | (1) 1인 1링크 토큰은 추측 불가능해야 함(보안) (2) 참여자 응답은 최대 1~2번 탭으로 끝나야 함(§0.5 "노동을 늘리지 않는다" 철학) (3) 실시간까지는 아니어도 새로고침 시 최신 상태 반영 (4) 가족 간 금전(정산)은 실제 송금 연동 없이 계산·기록까지만(관계 리스크 회피) |
| ⑧ 성공 지표 | **정정(2026-08-17): PRD §14에 이미 있었음** — 최상위 지표는 "가구 단위 반복 조율률"(첫 식사 후 2주 내 두 번째 식사를 만들고 확정한 비율), 그 외 링크 응답률·식사 확정률·확정 소요시간·반복 연락 감소·기록 재사용률·역할 교차율(v0.5 §14, v0.6에서도 유지). 처음에 "PRD에 없다"고 잘못 적었던 부분을 바로잡음 — v0.5 §14 전체를 안 읽고 v0.6의 "동일"이라는 한 줄만 보고 판단한 실수. |
