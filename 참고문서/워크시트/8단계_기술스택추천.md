# 8단계. 기술 스택(개발 스펙) 추천

> 🔖 참고: 프로젝트 메모리 기준 "실제 개발 착수는 다른 폴더로 이동해서 진행할 예정"이라 여기 추천은 그 시점에 실제로 쓸 스택 후보.

## ① PRD 기반 스택 추천받기

| 층(Layer) | 후보 1 | 후보 2 | 선택 이유 |
|---|---|---|---|
| 프론트엔드 | 지금의 정적 HTML + Tailwind CDN 유지, Supabase JS SDK로 직접 연동 | Next.js(React) — Vercel 배포, AI 코드생성 도구와 호환성 높음 | 1인 비개발자·바이브코딩 학습자에게는 지금 이미 손에 익은 패턴(정적 HTML)을 유지한 채 데이터만 실제 DB로 바꾸는 게 학습 부담이 가장 낮음 |
| 백엔드/DB | Supabase | Firebase | Supabase는 Postgres 기반이라 6단계에서 이미 설계한 관계형 테이블 구조(households→meals→meal_participants)를 그대로 옮기기 좋고, 인증·API가 통합돼 있어 백엔드 코드를 따로 안 짜도 됨 |
| 배포 | Vercel (프론트) + Supabase 자체 호스팅(DB) | Netlify | Vercel은 정적 HTML도, 나중에 Next.js로 전환해도 그대로 쓸 수 있어 배포 방식을 두 번 안 바꿔도 됨 |

## ② 경량/확장 버전 비교표로 다듬기

| 층(Layer) | 경량 버전 | 확장 버전 | 우리 프로젝트에 맞는 선택 |
|---|---|---|---|
| 프론트엔드 | 지금의 정적 HTML 35개 파일을 그대로 두고, `localStorage` 호출부만 Supabase JS SDK 호출로 하나씩 교체 | Next.js로 전면 재작성, 컴포넌트 재사용·상태관리 도입 | **경량** — 이미 완성된 화면·흐름을 그대로 살릴 수 있고, 프레임워크 학습이라는 새 장벽이 안 생김 |
| 백엔드/DB | Supabase 테이블 + Row Level Security만 적용 | Supabase + Edge Functions로 복잡한 비즈니스 로직(반복 일정 자동 생성 등) 서버 처리 | **경량 먼저** — 반복 일정 자동 생성 같은 로직은 지금처럼 클라이언트에서 처리해도 충분히 검증 가능 |
| 배포 | Vercel 무료 플랜 | Vercel Pro + 커스텀 도메인 | **경량** — 실사용 검증 전까지는 무료 플랜으로 충분 |

**최종 선택 이유 (페르소나·프로젝트 상황과 연결)**: 페르소나(이정숙)의 기술 친숙도가 "복잡한 설정은 부담스러워함"이었고, 이건 사실 개발자인 나(사용자)에게도 그대로 적용됨 — 프레임워크를 새로 배우는 것보다 이미 동작 검증된 정적 목업을 그대로 살려 데이터 레이어만 바꾸는 경량 버전이, 지금 단계(실사용 검증 전)에 가장 위험이 적은 선택이다. 확장 버전(Next.js)은 실사용자가 늘어나 유지보수·상태관리 부담이 실제로 느껴질 때 넘어가도 늦지 않음.

## ③ 검증 — PRD·페르소나와 대조하기

| 확인 항목 (비기능 요구사항 / 페르소나 기술 친숙도) | 추천 스택과 일치 여부 (O/X) | 조정 필요 사항 |
|---|---|---|
| 참여자 응답은 최대 1~2번 탭 (§0.5 철학) | O | 정적 HTML+Supabase SDK 조합이라 응답 화면 자체의 탭 수는 스택과 무관하게 그대로 유지됨 |
| 1인 1링크 토큰은 추측 불가능해야 함(보안) | O | Supabase RLS + UUID 기반 링크로 충족 가능.단, 실제 토큰 발급 로직은 아직 설계 전 — 개발 착수 시 첫 작업으로 필요 |
| 가족 간 금전(정산)은 실제 송금 연동 없음 | O | 정산은 계산·기록까지만, 결제 게이트웨이 연동 자체가 없으므로 스택 선택과 무관 |
| 페르소나 기술 친숙도(복잡한 설정 회피) | O | 경량 버전 선택 이유와 정확히 일치 — 개발자 본인도 같은 이유로 경량을 택함 |
