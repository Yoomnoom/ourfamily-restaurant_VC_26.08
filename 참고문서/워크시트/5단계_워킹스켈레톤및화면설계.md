# 5단계. 워킹 스켈레톤 & 화면설계

## ① 워킹 스켈레톤의 기본 구조와 사용자 흐름 설계하기

> 화면 흐름은 사용자가 화면을 이동하는 동적인 순서(4단계 사이트맵의 정적 목록과는 다름). 실제 완성된 정적 목업(`0. 확인용뷰어`) 기준의 핵심 루프.

| 단계 | 화면 요소 (버튼/입력필드 등) | 설명 |
|---|---|---|
| 1단계: 홈 / 내 식탁 | [버튼] 식사 만들기(FAB), [카드] 오늘/내일 식사 요약, [원형 히어로] 오늘 좌석 현황 | 오늘 누가 먹는지 한눈에 보여주고, 새 식사를 시작하는 진입점 |
| 2단계: 식사 만들기 | [입력] 날짜·시간, [태그입력] 메뉴, [체크리스트] 참여 대상, [버튼] 저장 | 메뉴·시간·대상을 정하고 참여자별 링크를 만들 준비 |
| 3단계: 참여자 링크 공유 | [목록] 참여자별 고유 링크, [버튼] 공유하기 | 1인 1링크를 각자에게 전달 |
| 4단계: 참여자 응답 | [버튼] 먹어요/안 먹어요, [선택] 도착시간, [입력] 선택형 한 줄 요청 | 가입 없이 링크만으로 짧게 응답 |
| 5단계: 확정 전 요약 | [영역] 예상 준비 인원 자동 계산, [경고] 미응답자 표시, [버튼] 확정하기 | 인원을 다시 계산할 필요 없이 바로 확정 판단 |
| 6단계: 오늘의 식탁 완성 | [요약] 최종 메뉴·시간·인원, [버튼] 다시 열기 | 확정 결과를 닫고 기록으로 남김 |

## ② 아이디어를 기획 초안 문서로 다듬기

| 항목 | 내용 |
|---|---|
| 워킹 스켈레톤의 주요 목표 | "1인 1링크 무가입 응답으로 가입 없이도 짧게 답할 수 있다"와 "예상 준비 인원이 자동 계산된다"는 두 핵심 가치가 실제로 동작하는지 검증 |
| 포함될 핵심 기능 목록 | 식사 만들기, 1인 1링크 공유, 무가입 응답(먹어요/안 먹어요·도착시간), 확정 전 요약(자동 인원 계산), 오늘의 식탁 확정 |
| 각 기능이 반드시 포함되어야 하는 이유 (페르소나 근거) | 이정숙(3단계 최종 페르소나)의 핵심 목표가 "남는 음식 없이 메뉴·인원을 빨리 확정"이고, 페인포인트가 "답변 지연·계획 변경·기록 단절"이라 이 다섯 기능이 그 목표·페인포인트를 직접 커버해야 워킹 스켈레톤의 의미가 있음 |
| 핵심 사용자 흐름 요약 | 홈에서 식사 만들기 → 참여자에게 링크 공유 → 참여자가 가입 없이 응답 → 확정 전 요약에서 자동 계산된 인원 확인 → 오늘의 식탁으로 확정 |

## ③ 실제 시안 제작

> 🔖 메모: 원래 워크시트는 Claude Design/Google Stitch로 시안을 만드는 걸 전제로 하는데, 이 프로젝트는 처음부터 Tailwind CDN + vanilla JS 정적 HTML로 직접 화면을 만들었어(디자인 툴 대신 실제 동작하는 목업을 바로 만든 셈). 스크린샷/링크 대신 아래로 대체함.

- 완성된 화면: 총 35개 정적 HTML 화면(온보딩 4, 로그인 2, 핵심 루프 9, 달력·기록 2, 가구관리 4, 살림 4, 로드맵 4, 확인용 도구 1 등)
- 한 번에 훑어보는 방법: `0. 확인용뷰어/code.html`을 열면 페르소나별·기기별로 전체 화면을 iframe으로 넘겨보며 확인 가능
- 디자인 톤: "Warm Table" — 무채색 M3 그레이 팔레트(의도적 선택, 라벤더 등 파스텔은 시도 후 기각됨), 카드 rounded-xl/2xl, 버튼 rounded-full로 통일
