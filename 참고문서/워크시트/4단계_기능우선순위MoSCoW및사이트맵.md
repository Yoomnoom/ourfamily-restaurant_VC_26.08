**① 기능 브레인스토밍 & MoSCoW 분류**

3단계에서 만든 페르소나·저니맵·컨셉 스테이트먼트를 근거로, 서비스에 필요한 기능 후보를 최대한 많이 떠올린 뒤 Must/Should/Could/Won't로 분류합니다.

**📝 프롬프트 예시**

1~3단계에서 작성한 워크시트 파일(문제정의·근본원인, 페르소나, 저니맵, 컨셉 스테이트먼트가 담긴 파일)을 첨부해줘. 이 내용을 참고해서, 서비스에 필요한 핵심 기능 후보들을 Must / Should / Could / Won't로 분류해줘. 각 기능이 왜 그 등급인지 이유를 페르소나의 목표·페인포인트와 연결해서 설명해줘. Won't로 분류한 기능은 지금 단계에서 제외하는 이유도 한 줄씩 적어줘. UI 디자인은 전혀 고려하지 않아도 돼.

**🤖 모의 예시 (냉장고 파수꾼)**

| **기능 후보** | **등급 (Must/Should/Could/Won't)** | **근거 (페르소나 목표·페인포인트 연결)** |
|---|---|---|
| *사진 한 장으로 재료 자동 등록* | *Must* | *핵심 페인포인트인 '수동 입력의 번거로움'을 직접 해결* |
| *재고 목록 조회* | *Must* | *등록만 하고 확인을 못하면 서비스 존재 이유가 사라짐* |
| *유통기한 임박 알림* | *Should* | *낭비 방지 목표에 직결되지만, 등록·조회 없이는 작동 불가* |
| *재료별 추천 레시피* | *Could* | *있으면 좋지만 핵심 문제 해결과는 직접 관련 없음* |
| *커뮤니티 게시판* | *Won't* | *'빠르게 확인하고 끝내기' 니즈와 반대되는 기능이라 지금 단계에서 제외* |

**✏️ 학생용 워크시트 — 내 프로젝트로 채우기**

| **기능 후보** | **등급 (Must/Should/Could/Won't)** | **근거 (페르소나 목표·페인포인트 연결)** |
|---|---|---|
| 가구·구성원 등록(색·평소 기본값) | **Must** | 이정숙이 매번 누가 먹는지 다시 묻는 노동을 줄이고, 평소 패턴을 참고 정보로 남기기 위한 기초 데이터다. |
| 식사 생성(하루 여러 건·시간 기준) | **Must** | 계획 변경과 고정되지 않은 식사 시간을 흡수해야 메뉴·인원을 빠르게 확정할 수 있다. |
| 1인 1고유 링크·무가입 응답 | **Must** | 참여자는 짧게 답하는 경향이 있어 가입·이름 선택이 붙으면 응답 지연이라는 근본 문제가 반복된다. |
| 먹어요·안 먹어요 응답 | **Must** | 참여 여부를 가장 짧게 수집해 준비 인원 계산으로 연결하는 핵심 입력이다. |
| 도착시간 원터치 선택 | **Must** | 이정숙의 실제 준비 판단에는 참석 여부뿐 아니라 제때 오는지가 중요하다. 단, 참여자 직접 인터뷰로 재검증할 가설이다. |
| 미응답 분리 | **Must** | 답변 지연을 자동 불참으로 오해하지 않고, 확인 전 상태를 별도로 관리해야 음식 준비 오류를 줄일 수 있다. |
| 예상·최종 준비 인원 계산 | **Must** | 흩어진 답을 머릿속으로 다시 계산하는 노동을 없애는 제품의 핵심 가치다. |
| 미응답 상태의 확정 경고·확정 허용 | **Must** | 답이 늦어도 준비 결정을 멈추지 않되, 누락 위험은 놓치지 않도록 한다. |
| 오늘의 식탁 확정·완료 | **Must** | 메뉴·시간·인원을 한 결과로 닫아야 이정숙의 목표가 완료되고 다음 기록으로 이어진다. |
| 식사 카드 목록·달력 확인 | **Must** | 하루 여러 식사와 변경된 계획을 한곳에서 확인해 다시 묻거나 기억하는 일을 줄인다. |
| 식사별 개설자·참여자 권한 | **Must** | 사람을 고정 역할로 나누지 않고, 각 식사에서 만든 사람과 응답자를 구분해야 실제 가족 관계를 반영할 수 있다. |
| 응답 변경 감지·개설자 알림 | **Must** | 계획 변경을 이정숙이 놓치면 준비 인원이 다시 틀어지므로 변경 사실이 자동 반영되어야 한다. |
| 식사 자동 기록 | **Must** | 확정 결과가 다음날 사라지지 않게 해 기록 단절을 해결하고 재사용의 기반을 만든다. |
| 지난 구성으로 새 식사 만들기 | **Must** | 지난 결정이 다음 계획에 재사용되지 않는 5 Whys의 마지막 근본 원인을 직접 해결한다. |
| 반복 손님 저장 | **Must** | 자주 오는 가족 외 참여자를 매번 새로 입력하는 조율 노동을 줄인다. |
| 월 요약 통계(횟수) | **Must** | 기록이 실제로 축적·집계되는지 검증하는 최소 통계이며, 고급 분석은 포함하지 않는다. |
| 선택형 한 줄 요청 | **Should** | 늦음·몫 남기기 같은 생활 정보를 보완하지만, 참여자의 짧은 응답 습관을 해치지 않도록 선택 입력으로 둔다. |
| 참여자 응답 수정 | **Should** | 계획 변경을 직접 반영할 수 있으나 초기에는 개설자 대리 입력으로도 핵심 루프를 유지할 수 있다. |
| 개설자 대리 입력 | **Should** | 어르신·어린이의 접근성 문제를 줄이지만, 초기에는 수동 확인 후 개설자가 결과만 관리하는 방식으로 대체 가능하다. |
| 미응답자 링크 재공유 | **Should** | 답변 지연을 줄이지만 기존 카카오톡 재전송으로 임시 대체할 수 있다. |
| 확정 식사 다시 열기 | **Should** | 확정 뒤 계획 변경에 대응하지만 발생 빈도가 낮아 최초 확정 루프보다 후순위다. |
| 요일별 평소 기본값 | **Could** | 반복 패턴 활용 가능성은 있으나 초기에는 단일 평소 기본값만으로도 충분하다. |
| 메뉴 추천 칩 | **Could** | 식사 생성 편의는 높이지만 인원·메뉴 확정의 핵심 병목을 직접 해결하지 않는다. |
| 반복 일정 | **Could** | 특별한 날 외 역할 교대가 드물어 초기 검증 가치가 낮다. |
| 고급 기록 검색 | **Could** | MVP에는 검색할 만큼 기록이 쌓이지 않아 선행 가치가 낮다. |
| 주문 관리·주문번호·주방 칸반 | **Won't** | 공동 식사 조율 서비스의 정체성을 음식점 운영 도구로 흐리기 때문에 제외한다. |
| 결제·매출 | **Won't** | 페르소나의 인원·메뉴 확정 목표와 무관하고 가족 간 금전 문제라는 별도 리스크를 만든다. |
| 메뉴별 수량 주문·필수 옵션 | **Won't** | 짧은 응답 원칙과 반대로 참여자의 입력 노동을 크게 늘린다. |
| 고정 역할(셰프·손님) | **Won't** | 가족에게 위계를 만들지 않고 식사마다 역할이 바뀐다는 제품 철학과 충돌한다. |
| AI 메뉴·음식 이미지 추천 | **Won't** | 추천 근거가 될 실제 사용 데이터가 아직 없고 핵심 조율 문제보다 범위가 크다. |
| 앱 내 보이스톡 | **Won't** | 통신 기능 개발 부담이 크며 기존 전화·메신저로 충분히 대체 가능하다. |
| 정밀 영양 정보 | **Won't** | 서비스 목표는 식사 참여와 준비 인원 확정이지 건강·영양 관리가 아니다. |
| 음식 사진 기록 | **Won't** | 입력 노동과 저장 비용을 늘리며 기록 재사용에 필수적이지 않다. |
| 밀키트 자동 제안 | **Won't** | 사용 데이터와 추천 정확도가 확보되기 전에는 제안 근거가 없어 MVP에서 제외한다. |

*💡 Won't로 분류하는 것도 근거가 있어야 합니다 — '왜 지금은 안 하는지'까지 적어보세요.*

**② 사이트맵 작성**

Must + Should로 분류된 기능만 화면 단위로 묶어 사이트맵(정적인 화면 계층 구조)을 만듭니다. 사용자가 이동하는 순서(화면 흐름)와는 다른, '어떤 화면들이 있는지'에 대한 지도입니다.

**📝 프롬프트 예시**

방금 분류한 Must + Should 기능들을 화면 단위로 묶어서 사이트맵을 만들어줘. 사이트맵은 화면들의 정적인 목록·계층 구조이며(사용자가 이동하는 순서가 아님), 최상위 화면부터 하위 화면까지 트리 구조로 보여주고 각 화면에 어떤 기능이 들어가는지 한 줄씩 설명해줘.

**🤖 모의 예시 (냉장고 파수꾼)**

| **최상위 화면** | **하위 화면** | **포함되는 기능** |
|---|---|---|
| *홈* | *—* | *재료 등록·재고 목록·소비 처리로 이동하는 진입점* |
| *재료 등록* | *사진 촬영* | *사진 한 장으로 재료 자동 등록* |
| *재고 목록* | *유통기한 임박 알림* | *재고 목록 화면 안에 임박 항목 강조 표시* |
| *소비 처리* | *—* | *다 먹음 / 버림 처리* |

**③ 검증 — 1~3단계 원본과 대조하기**

MoSCoW 분류와 사이트맵이 완성되면, 이 결과가 1~3단계 원본(페르소나·저니맵·컨셉 스테이트먼트)의 핵심 내용을 빠뜨리지 않았는지 대조합니다. 만들기만 하고 넘어가면 AI가 요약 과정에서 놓친 부분을 그대로 안고 다음 단계로 가게 됩니다.

**📝 프롬프트 예시**

방금 분류한 MoSCoW 결과와 사이트맵을 1~3단계 원본 워크시트 파일과 대조해줘. 페르소나의 핵심 목표·페인포인트 중 어떤 기능에도 반영되지 않은 항목이 있는지 확인해줘. 빠진 부분이 있다면 어느 등급(Must/Should/Could)에 추가하면 좋을지 제안해줘.
